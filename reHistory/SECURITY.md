# Аудит безопасности reHistory

Дата: 28 октября 2026 года. Проведена отдельная самостоятельная проверка реализации после этапа разработки ядра, после разработки диалога и после интеграционных тестов. Это проверка кода и поведения на тестовых репозиториях, а не независимая сертификация.

## Область проверки

Проверены `engine.ts`, `cli.ts`, инструкции по запуску и восстановлению. Основные риски: потеря истории, изменение посторонних веток, выполнение команд из пользовательского ввода или метаданных Git, частичное применение, скрытые записи при dry-run и неверная работа с merge-графом.

## Найденное и исправленное

1. Путь к признакам незавершённых Git-операций первоначально мог проверяться относительно каталога запуска. Исправлено на абсолютные пути выбранного репозитория через `rev-parse --path-format=absolute --git-path`. Регрессионный тест запускается из другого каталога и проверяет `MERGE_HEAD`.
2. Для незатрагиваемых прямых ссылок первоначально формировались обновления с тем же хешем. Заменено на `verify`: текущая ветка и её теги обновляются, остальные ссылки только проверяются.
3. Проверка partial clone первоначально распознавала только буквальное значение `promisor=true`. Теперь любая настройка `remote.*.promisor` или `extensions.partialclone` блокирует запуск, включая отключённую настройку: это намеренно консервативное ограничение. Дополнительно передаётся `GIT_NO_LAZY_FETCH=1`; основная защита на старых Git — предварительный отказ для partial clone.
4. Добавлены отказ для символических локальных веток/тегов, запрет управления Git через наследуемые `GIT_*` и ограничение суммарного размера создаваемых метаданных 128 МиБ.
5. Подписи и заголовки `mergetag` не копируются в изменённые объекты как якобы действительные. Их удаление показывается в плане и требует отдельного согласия.

## Проверенные меры

- Вызовы Git используют `spawnSync` с массивом аргументов, без shell и строковой интерполяции команд. Перенаправление CLI-ответов запрещено: перед записью требуется интерактивный терминал и явный выбор пользователя.
- Имя бекап-ветки проверяется самим Git. Существующая ссылка не перезаписывается. Имя/email и даты валидируются, вывод из репозитория очищается от управляющих символов терминала.
- Hooks, fsmonitor, auto maintenance/gc и replace отключены. `push`, `fetch`, `reset --hard`, удаление refs/reflog/объектов не вызываются.
- Чистота репозитория, HEAD, незавершённые операции и набор ссылок проверяются до планирования и перед применением. Неподдерживаемые состояния приводят к отказу.
- Новые коммиты сохраняют деревья, сообщения и упорядоченные ссылки на родителей; новые даты строго возрастают в топологическом порядке. Двоичные данные сообщения не перекодируются.
- Dry-run сравнен с побайтовым снимком всех файлов `.git`: изменений нет.
- Файл восстановления создаётся эксклюзивно с POSIX-правами `0600`, до изменения refs, и синхронизируется через `fsync`. Эксклюзивное создание исключает перезапись существующего файла/символической ссылки.
- Обновление выбранной ветки/тегов и создание всех бекапов выполняются одной транзакцией с проверкой старых хешей. Проверена ошибка создания вложенной бекап-ссылки: исходные ссылки остаются неизменными.
- Файл `rehistory.lock` исключает второе применение reHistory. При ошибке штатно освобождается; чужая блокировка автоматически не удаляется.
- Проверено восстановление ветки и тегов из JSON одной обратной транзакцией с проверкой ожидаемых новых хешей.

## Воспроизводимая проверка

```sh
node --test reHistory/engine.test.ts
```

14 интеграционных тестов успешно выполнены на macOS, Node.js 24.12.0, Git 2.39.5. Включены SHA-1/SHA-256, bare-репозиторий, merge, lightweight/annotated/вложенные теги, другие ветки/remote-tracking refs, бекап и его конфликт, dry-run, изменение идентичности, восстановление, грязное дерево, detached HEAD, stash, shallow/partial clone, grafts, worktree, поддельные подписи, побайтовое сохранение сообщения, hooks, блокировка второго процесса и переменные окружения. Форматы подписей проверяются на синтетических блоках; полноценное создание/проверка криптографических подписей в тестах не выполняется.

Дополнительно в PTY на отдельном временном репозитории проверены интерактивные dry-run и реальное применение с бекапом; после применения выполнен `git fsck --strict`. Тестовые коммиты и ветки создаются только во временных репозиториях; история самого Toolchain не переписывалась.

## Оставшиеся ограничения

- Другие процессы Git не соблюдают `rehistory.lock`. Работа требует отсутствия параллельных операций Git/IDE/GC. Проверки хешей и снимка refs уменьшают риск, но не устраняют все гонки, особенно переключение HEAD, создание новых refs и изменения файлов сразу после последней проверки.
- Требуются доверенные локальные репозитории, Git executable в PATH, системная конфигурация и файловая система. Это не песочница для враждебных конфигураций или пользователей, одновременно меняющих служебные файлы Git.
- Транзакция refs не заменяет независимый бекап и не гарантирует восстановление после сбоя питания/диска. Читатели нескольких refs могут увидеть промежуточное состояние при обновлении файлового хранилища ссылок.
- После ошибки/аварийного прерывания могут остаться новые недостижимые объекты, файл восстановления или файл блокировки. Их нельзя автоматически удалять, пока не установлено фактическое состояние истории.
- При отказе от бекапа JSON не удерживает старые объекты от GC. Reflog и чужие копии могут сохранять старые даты независимо от выбора бекапа.
- Подписи удаляются с согласия пользователя, повторное подписание не выполняется. Теги общие для всего репозитория: тег на общем предке изменится, хотя другая ветка останется неизменной.
- Windows/Linux отдельно не тестировались. Для очень больших историй алгоритм запускает несколько процессов Git на объект и хранит план в памяти; при превышении лимита отказывает до изменения refs.

Обнаруженные дефекты исправлены, все включённые проверки проходят. Известные ограничения отражены в пользовательской документации.
