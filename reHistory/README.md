# reHistory

Интерактивное переписывание дат **всех коммитов, достижимых из текущей локальной ветки**, и соответствующих тегов. TypeScript запускается прямо в Node.js, без сборки и без npm-зависимостей.

## Требования и запуск

- Node.js 24 или новее; рекомендуется 24.12+. В корне Toolchain уже указан Node.js 24 в `.nvmrc`.
- Git 2.39 или новее.
- Терминал с интерактивным вводом (TTY).
- Основная платформа — macOS. Используются стандартные API Node.js и Git, без bash в реализации. Windows и Linux отдельно не проверялись.

Из любого каталога:

```sh
node /абсолютный/путь/toolchain/reHistory/cli.ts --repo /путь/к/репозиторию --dry-run
node /абсолютный/путь/toolchain/reHistory/cli.ts --repo /путь/к/репозиторию
```

Если `--repo` не задан, используется текущий каталог. Поддерживаются пробелы в путях (в оболочке заключайте такие пути в кавычки). `--help` показывает справку. Установка пакетов не требуется.

Сначала рекомендуется dry-run на отдельном полном клоне. Клон с `git clone --no-local` не разделяет хранилище объектов с исходным локальным репозиторием.

## Диалог

1. **Бекап** — выбор «Да/Нет», по умолчанию «Да». Затем ввод имени ветки с предложенным значением `rehistory-backup/<время-UTC>`. Можно выбрать другое допустимое имя Git. Существующая ветка не перезаписывается. Ветка сохраняет исходную вершину текущей истории. Дополнительно создаются резервные ссылки на исходную текущую ветку и все затронутые теги в `refs/rehistory/backups/<уникальный-id>/…`.
2. **Интервал** — целое число секунд, по умолчанию `1`. Допустимы значения от 1 до 31536000.
3. **Начало истории** — сегодня в местном часовом поясе в `00:00:00`. Enter принимает предложенную дату. Можно ввести другую дату `2026-10-28` или точное время с обязательным часовым поясом: `2026-10-28T18:30:00+01:00` либо `2026-10-28T17:30:00Z`. Часовой пояс берётся из настроек системы, если задана только дата. Новые даты Git записываются в UTC (`+0000`). Дата относится к первому коммиту; последующие следуют после неё, поэтому последние даты могут оказаться в будущем.
4. **Идентичность** — выбор «Да/Нет», по умолчанию «Нет». При согласии имя и email заменяются **и у автора, и у коммитера каждого коммита**. При отказе исходные имена/email каждого сохраняются. Имя и email вводятся вручную; значения из Git config автоматически не подставляются во избежание случайного использования рабочей идентичности.
5. **План** — количество коммитов, даты начала/конца, интервал, идентичность, бекап, полный список меняющихся ссылок и старые/новые хеши. При наличии подписей отдельно запрашивается согласие на их удаление.
6. **Применение** — отдельное подтверждение с ответом «Нет» по умолчанию. В dry-run подтверждение не требуется: после плана выполнение заканчивается без записей.

Номера `1`/`2` выбирают варианты; Enter принимает значение по умолчанию. Ctrl+C отменяет диалог. Не закрывайте терминал и не прерывайте процесс во время применения.

## Что именно меняется

- Даты автора (`author date`) и коммитера (`committer date`) каждого коммита становятся одинаковыми.
- Коммиты обходятся от родителей к потомкам. Между соседними коммитами этого общего порядка задан ровно один интервал. В merge-графе разница между конкретным родителем и потомком может составить несколько интервалов. Порядок соседних независимых линий определяется топологическим обходом Git; родитель всегда раньше потомка.
- Переписывается только текущая локальная ветка. **Другие локальные ветки и remote-tracking ссылки, например `origin/main`, остаются как есть**, даже если содержат общих предков: в них сохраняется старая история.
- «Соответствующий тег» означает тег, чей конечный объект — коммит, достижимый из текущей ветки. Включаются lightweight, annotated и вложенные annotated-теги, в том числе теги на общих предках с другими ветками. **Тег глобален для репозитория**, поэтому изменение такого тега видно и при просмотре других веток. Теги на коммитах вне текущей истории, blob и tree не меняются.
- Сохраняются деревья, файлы, сообщения коммитов и порядок родителей, включая merge-коммиты и пустые коммиты. Сообщения сохраняются побайтно, без перекодирования. Изменение метаданных меняет хеши и ссылки на родителей.
- У annotated-тегов обновляются ссылки на объекты, сохраняются имя, tagger, дата создания тега и текст сообщения.
- Криптографические подписи коммитов и тегов после изменения объектов не могут оставаться действительными. Удаляются заголовки `gpgsig`, `gpgsig-sha256`, `mergetag` и стандартные блоки подписей тегов. `mergetag` удаляется целиком, потому что относится к исходному родителю. Наличие таких данных показывается в плане; реальное применение требует дополнительного согласия. Новые подписи не создаются.
- Рабочие файлы и индекс не переписываются. `push`, `fetch`, очистка reflog, удаление старых объектов и `gc` не выполняются.

Переписывание локальной истории **не гарантирует удаления старых дат** из чужих клонов, серверов, PR, CI, резервных копий или reflog. Оно также не устанавливает фактическое время выполнения работы. Gitlinks подмодулей сохраняются: история самих подмодулей не переписывается.

## Защита при выполнении

До работы и перед обновлением ссылок проверяются чистота рабочего дерева/индекса, HEAD, ссылки и незавершённые операции. Untracked-файлы также блокируют запуск. Игнорируемые файлы разрешены: утилита их не читает и не меняет.

Утилита отказывается работать с:

- detached/unborn HEAD;
- shallow-репозиторием, partial clone;
- дополнительными worktree;
- незавершёнными merge, rebase, cherry-pick, revert, sequencer или bisect;
- grafts и ссылками stash, notes, replace и другими неподдерживаемыми пространствами имён;
- символическими локальными ветками/тегами;
- метаданными создаваемых объектов суммарно больше 128 МиБ (деревья и содержимое файлов в этот лимит не входят).

Обычный полный bare-репозиторий поддерживается. Пустой репозиторий без коммитов не поддерживается. Поддерживаются хеши SHA-1 и SHA-256.

Git вызывается без shell, пользовательские данные не становятся командами. Наследуемые переменные `GIT_*` исключаются из окружения дочернего Git: перенаправления через `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG_*` и т. п. намеренно не используются; выбирайте репозиторий через `--repo`. Локальные hooks, fsmonitor, автоматические maintenance/gc и replace-объекты отключены для вызовов утилиты. Скрипт предназначен для доверенных локальных репозиториев, а не изоляции произвольной враждебной Git-конфигурации.

План вычисляет хеши без `-w`. **Dry-run не создаёт ни объектов, ни бекапов, ни файлов восстановления/блокировки.** При применении сначала создаются файл восстановления и новые объекты, затем все изменения ветки, тегов и создание резервных ссылок проходят одной транзакцией `git update-ref --stdin` с проверкой исходных хешей. Если подготовка транзакции не удалась, ссылки не обновляются. Новые недостижимые объекты и файл восстановления при такой ошибке могут остаться.

`rehistory.lock` в общем каталоге Git исключает одновременное применение второго экземпляра reHistory. **Другие программы Git эту блокировку не соблюдают.** Закройте Git-интеграцию IDE и не запускайте параллельно Git-команды, фоновые синхронизации и сборку мусора. Проверки исходных значений снижают риск гонок, но не заменяют эксклюзивную работу с репозиторием. Сбой питания/носителя не покрывается транзакционными гарантиями приложения.

## Восстановление

После применения выводятся пути к резервным ссылкам (если бекап включён) и файлу `rehistory-recovery-<id>.json` в общем каталоге Git. Этот файл имеет права `0600` на POSIX и содержит для каждой затронутой ссылки:

- `name` — полное имя ссылки;
- `old` — исходный хеш;
- `new` — хеш после переписывания.

Файл создаётся до записи объектов. Само его наличие **не означает**, что переписывание состоялось: после сбоя сравните фактические ссылки с полями `old`/`new`.

Чтобы вернуть все исходные ссылки, завершите другие операции Git, проверьте чистоту рабочего дерева и создайте обычный текстовый файл с командами, подставив значения из JSON:

```text
start
option no-deref
update <name-ветки> <old-ветки> <new-ветки>
option no-deref
update <name-тега> <old-тега> <new-тега>
prepare
commit
```

Добавьте по одной строке `option no-deref` и `update` **для каждой** записи `refs` из файла восстановления. Угловые скобки — обозначения значений; в итоговом файле их быть не должно. Выполните из нужного репозитория:

```sh
git -c core.hooksPath= update-ref --stdin < /путь/к/командам-восстановления.txt
git fsck --strict
```

Проверка `new` не даст случайно затереть новые коммиты, появившиеся после переписывания. При несовпадении остановитесь и разберите изменения, не убирайте эту проверку. Бекап-ветка и резервные ссылки после восстановления сохраняются. Не используйте `reset --hard` для восстановления метаданных: содержимое файлов не менялось.

Если бекап был отключён, JSON сохраняет только хеши. Старые объекты могут какое-то время оставаться в reflog/хранилище, но **после сборки мусора восстановление по ним не гарантируется**. Для важных репозиториев дополнительно сохраните отдельный полный клон на другом носителе.

Если процесс аварийно завершился и остался `rehistory.lock`, сначала убедитесь, что никакой экземпляр утилиты не работает (в файле записан PID). Сохраните файл восстановления, проверьте состояние ссылок и лишь затем удалите оставшийся файл блокировки вручную. Скрипт автоматически чужую блокировку не удаляет.

Резервные ссылки содержат старую историю. Удаляйте их и бекап-ветку только после проверки результата и сохранения независимой копии. Скрипт их самостоятельно не удаляет. При повторном запуске из обычной ветки существующие бекапы не переписываются; запуск из самой бекап-ветки, как из любой текущей ветки, перепишет её историю.

## Проверки разработки

```sh
node --test /абсолютный/путь/toolchain/reHistory/engine.test.ts
```

Интеграционные тесты создают и удаляют собственные временные репозитории; историю Toolchain не меняют. Подробности проведённого аудита и оставшихся ограничений — в [SECURITY.md](SECURITY.md).

Справочные первоисточники: [прямой запуск TypeScript в Node.js](https://nodejs.org/api/typescript.html), [транзакции git update-ref](https://git-scm.com/docs/git-update-ref).
